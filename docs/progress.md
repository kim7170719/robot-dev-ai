## G12.5 v0.4 composable architecture refactor (started)

The user-supplied v0.4 roadmap supersedes the future v0.3 sequence without
rewriting historical evidence. G12.5 will make architecture, capability,
composition, adapter, readiness, safety, resource, and evidence states
first-class before resuming M15. `docs/roadmap_v0.4.md` records the acceptance
criteria and `docs/architecture_v0.4.md` records the whole-system boundary.
Status is architecture/document baseline only; no G12.5 code or gate claim has
been made.

G12.5 Task 1 (2026-10-12): **PASS.** `registry.v04` now defines versioned
resource, hardware-profile, robot-spec, architecture-plan, and composition-plan
models. `migrate_v03_registry()` validates and retains the existing v0.3
registry inside a v0.4 envelope, then marks migrated hardware `unknown` rather
than inventing verification. Schema/migration tests plus the full suite passed:
**69 tests**. This establishes models only; Architecture Resolver behavior is
the next task and G12.5 remains open.

G12.5 Task 2 (2026-10-12): **PASS.** `agent.architecture_resolver` now
deterministically selects a topology from declared v0.4 hardware profiles and
robot requirements without generating files. It assigns ROS 2/Nav2 to a Linux
host and motor/encoder work to an MCU for Host+MCU requests; it honours explicit
topology choices, and returns `architecture-conflict` for an MCU-only navigation
request. It emits plans with `not-tested` evidence status rather than claiming
that an actual device is connected. Architecture tests plus the full suite
passed: **73 tests**. Task 3, capability/constraint registry upgrade, is next.

G12.5 Task 3 (2026-10-12): **PASS.** `RegistryDocumentV04` now validates
hardware profiles against declared software-driver, transport, and constraint
facts. Profiles record `driver_ids`, `constraint_ids`, `firmware_required`,
verification state, limitations, and provenance; the migration maps legacy
drivers into unknown-v0.4 software profiles rather than asserting support.
Unknown transport/driver/constraint references are rejected. The complete suite
passed: **75 tests**. Task 4, deterministic Composition Planner, is next.

G12.5 Task 4 (2026-10-12): **PASS.** `agent.composition_planner` turns an
architecture plan, a v0.4 registry, and a robot spec into a deterministic,
ordered component graph without rendering templates or writing files. It maps
known capabilities to their registry-authorized component templates and binds
the declared hardware profile. Unknown capabilities, absent hardware profiles,
and known capabilities without a component template return explicit blocked
issues rather than LLM-generated guesses. The complete suite passed: **77
tests**. Task 5, backward-compatible template componentization, is next.

G12.5 Task 5 (2026-10-12): **PASS.** `TemplateExpander.expand_composition()`
now renders an ordered `CompositionPlan` in memory from per-component values,
without repeating the v0.3 registry selection step. The original
hardware/capability-authorized `expand()` seam and safe writer remain intact.
Combined output is rejected before materialization when component templates
would claim the same destination path, so one component cannot silently
overwrite another. The complete suite passed: **79 tests**. Task 6, adapter
selection and validation, is next; G12.5 remains open.

G12.5 Task 6 (2026-10-12): **PASS.** The versioned registry now carries
traceable serial, micro-ROS, or ros2_control adapter contracts, each with
supported device classes plus declared transport and software-profile
requirements. `AdapterResolver.resolve()` is a pure, explicit adapter-selection
seam: it returns a selected contract only when those recorded facts match, or
returns missing-fact reasons. The initial verified serial-contract test passes;
it does not open serial ports, start ROS, flash firmware, or command hardware.
The complete suite passed: **80 tests**. Task 7, hardware readiness and safety
transactions, is next; G12.5 remains open.

G12.5 Task 7 (2026-10-12): **PASS.** `HardwareReadinessGate.evaluate()` now
evaluates only structured, attributable readiness observations. A device is
ready only when every explicitly required check has `pass` evidence; missing,
failed, or `not-tested` checks produce a stable `blocked` result. The gate does
not enumerate USB/CAN/serial devices, start ROS, or command hardware. The
complete suite passed: **82 tests**. Task 8, safety transaction semantics, is
next; G12.5 remains open.

G12.5 Task 8 (2026-10-12): **PASS.** `MutationSafetyGate.evaluate()` permits
only a proposed mutation with passed readiness, a reviewable diff, a rollback
description, and explicit human confirmation. It never applies the mutation.
The complete suite passed: **83 tests**. Task 9 is next.

G12.5 Task 9 (in progress, 2026-10-12): the acceptance suite now covers the
documented/undocumented unknown-device fallback: sources yield only a
human-approved provisional path, while absent sources are blocked. This is not

G12.5 Task 10 (2026-10-12): **PASS.** `GET /api/v1/core/schema` freezes a
